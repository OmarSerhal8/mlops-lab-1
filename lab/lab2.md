## Question 2

### What is the role of `--backend-store-uri` and `--default-artifact-root` in the MLflow server?

The MLflow server was started using:

```bash
uv run mlflow server --host 127.0.0.1 --port 5000 --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns
```

The option:

```text
--backend-store-uri sqlite:///mlflow.db
```

defines where MLflow stores experiment metadata such as:

- experiments
- runs
- parameters
- metrics
- run information

In this lab, this metadata is stored in the SQLite database:

```text
mlflow.db
```

The option:

```text
--default-artifact-root ./mlruns
```

defines the default location used to store artifacts generated by MLflow runs, such as trained models and their associated files.

Therefore:

```text
MLflow
├── mlflow.db → experiment metadata
└── mlruns/   → artifacts and model files
```

## Question 3

### Why should `mlflow.db` and `mlruns/` not be committed to Git? Should they be tracked by DVC?

Both are generated local MLflow outputs and should not be committed to Git.

They were therefore added to `.gitignore`:

```text
mlflow.db
mlruns/
```

`mlflow.db` contains local experiment metadata, while `mlruns/` contains generated MLflow artifacts.

They should also not be tracked by DVC in this project.

The responsibilities of the tools are separated as follows:

```text
Git    → source code and configuration
DVC    → dataset versions
MLflow → experiments, parameters, metrics and model artifacts
```

## Question 5

### What is the difference between a parameter and a metric in MLflow? Why do metrics use `step`?

A parameter represents a configuration value chosen for a training run.

Examples from this lab include:

```text
dataset
epochs
learning rate
batch size
model
```

They were logged once at the beginning of each run:

```python
mlflow.log_params({
    "dataset": args.dataset,
    "epochs": args.epochs,
    "lr": args.lr,
    "batch_size": args.batch_size,
    "model": "resnet18",
})
```

A metric represents a measured value produced during or after training.

Examples include:

```text
train_loss
val_loss
val_accuracy
test_accuracy
```

Metrics such as training loss and validation accuracy change after every epoch.

For example:

```python
mlflow.log_metric(
    "val_accuracy",
    val_accuracy,
    step=epoch,
)
```

The `step` argument associates each metric value with a specific training step or epoch.

This allows MLflow to display the evolution of a metric as a graph:

```text
Epoch 1 → val_accuracy
Epoch 2 → val_accuracy
Epoch 3 → val_accuracy
...
```

Parameters normally do not require a step because they remain fixed during the run.

## Question 7

### Compare the runs. How did the learning rate and batch size affect validation accuracy? Is higher validation accuracy always better?

Four successful configurations were compared:

| Learning Rate | Batch Size | Final Validation Accuracy | Test Accuracy |
|--------------:|-----------:|--------------------------:|--------------:|
| 0.01 | 32 | 0.1925 | 0.1880 |
| 0.001 | 32 | 0.4909 | 0.5073 |
| 0.0001 | 32 | 0.7673 | 0.8203 |
| 0.001 | 64 | 0.5319 | 0.5648 |

For the tested configurations, reducing the learning rate from `0.01` to `0.0001` produced substantially better validation performance.

The learning rate of `0.01` resulted in poor performance, while `0.0001` produced much better validation and test accuracy.

Changing the batch size from `32` to `64` while keeping the learning rate at `0.001` changed the final validation accuracy from approximately:

```text
0.4909 → 0.5319
```

However, these experiments alone are not sufficient to establish a general rule about batch size because only a small number of configurations were tested and training contains randomness.

A higher validation accuracy is generally useful when selecting among runs evaluated under the same conditions, but it should not automatically be interpreted as proof that a model is universally better.

Validation performance can be affected by randomness, the validation dataset, hyperparameter tuning, and overfitting to repeated validation decisions. Final model assessment should therefore also consider independent test performance and other relevant metrics.

```text

```

The two runs using:

```text

```

For the configurations tested in this lab, the learning rate therefore had a strong observed effect on validation performance. The smaller learning rate of `0.0001` was associated with the strongest validation result.

Because only four configurations were evaluated, this should be interpreted as an observed pattern for these experiments rather than a general conclusion about all learning rates and batch sizes.
